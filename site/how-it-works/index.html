How Huddle works

One task is one Issue, one branch and one pull request. Two roles, seven labels, and a rule: the AI never guesses at a decision that is not its to make.

Roles

Huddle has two roles. They are about people, not about the AI: every person has their own session, in Claude Code or OpenAI Codex, whichever they like. The Coach and the Players may mix the two tools at the same time, and one person can be both, on two plans. The sessions never talk to each other directly: they talk through GitHub or GitLab, with Issues, pull requests, comments and labels. Only design work still needs Claude Code.

Coach

One person per repo. They install Huddle, write the Issues, answer decisions, review pull requests and merge. Only they merge into the default branch, and only they touch production, settings and secrets.

Player

Takes an Issue, works on its own branch and answers what the session asks. Their session never merges, never touches the default branch or secrets, and touches only the files the Issue allows.

Why one Coach: decisions that nobody owns get answered in a rush, or twice in two ways. One owner keeps the answers consistent and keeps production in a single pair of hands. Each person runs one or two Issues at a time.

Labels

The status of an Issue lives in its labels. Nobody sets them by hand: the sessions do, with huddle labels, from each Issue's «Depends on» section and from its comments. There is no cloud job and it uses no CI minutes.

Every change to an Issue goes through a Huddle session: creating it, editing it, closing it, reopening it and merging its pull request. Still fine by hand on the website: reading and commenting, the bug report form, and a tester's «✅ Tested in staging» comment. It is a rule, not a lock: if someone breaks it, the next session that opens repairs the board by itself.

LabelMeaning
readyEverything it depends on is merged. Waiting for someone.
assignedA Player has it. Not started.
in progressA session is working on it.
in reviewA pull request is open and waits for the Coach.
blockedIt depends on an Issue that is not merged yet.
needs decisionThe session asked the Coach and waits.
changes requested from CoachThe Coach asked for changes and nobody has taken the request yet.

An Issue lists what it needs under «Depends on». A dependency counts as merged only when the Issue is closed and a merged pull request closed it. An Issue closed by hand unblocks nothing.

Two labels are stop labels: needs decision and changes requested from Coach. The work waits for someone else, so they stand alone: in progress and in review are taken off while one of them is on, and come back by themselves once the request is taken or the question is answered.

Areas and progress

A team sees how far each part of its project has come, as a percentage, and the total. Areas are milestones, on GitHub and on GitLab alike, and a project has as many as it needs. The Coach keeps an estimate of the Issues not written yet in each milestone, so the percentage is honest about the work still to come.

Progress shows in three places: a pinned «Huddle progress» Issue that rewrites itself, the huddle progress command, and one line when a Claude Code session opens. The skill /huddle-areas proposes the areas and puts Issues in them, and it changes nothing until the Coach says yes.

Decisions

Nothing is dropped silently. Everything an Issue asks for ends up done, or written under «What was NOT done» with the reason. When a session cannot go on without a decision, it does not guess:

  1. It pushes what is done.
  2. It comments on the Issue with the question, the options with their trade-offs and a recommendation, and adds the needs decision label.
  3. It stops. The Coach answers with /huddle-decide, and the session continues on the same branch.

Reviews

The session works test first: the failing test, then the code, touching only the allowed files. It opens the pull request with the real test counts and «What was NOT done», and ends with a message that starts with «Issue #N finished». CI runs the tests. The Coach reviews with /huddle-review and either merges or asks for changes.

A request for changes is a comment with a «Prompt for Claude Code» heading. The session waiting in the background picks it up, pushes the fix and answers «Ready for review again». The waiting is a small Node process on the Player's computer that asks GitHub or GitLab every two minutes, with the Player's own login: it uses no Claude tokens and no GitHub Actions or CI minutes. In OpenAI Codex the same wait runs as huddle wait <n> --codex, in a process of its own with no tokens, and wakes the open Codex chat when the Coach answers. If the session was closed meanwhile, a hook says on the next start that a request is pending. Either way, /huddle-play <n> picks the Issue up again after the Coach answered a review or a decision.

The Coach can also let their session do the checking: /huddle-watch looks every few minutes at what waits and reviews it (/huddle-watch status and /huddle-watch off do what they say). Turning it on is the order to merge what it approves. Decisions and bug triage stay with the person, and huddle queue lists what waits. The watch is turned on by hand in each session. It waits in the background like a Player's session, so it uses no Claude tokens while nothing waits, and wakes the session only when something waits. Without it, the Coach's session start says what waits. /huddle-watch always keeps it on: it starts again in each of the Coach's sessions of that repo on that machine (a mark on the machine, not a file of the repo), until /huddle-watch off. It never starts for a Player.

The Coach may watch from Codex too: $huddle-watch waits with no tokens and wakes the open Codex chat when something waits, and that chat reviews, requests changes, merges and lands. There is one watch per repo on a machine, whatever the tool: the first session that turns it on reviews, and another one says «The watch already runs in Codex…» (or in Claude Code) and does not start a second. If the owner goes quiet while it reviews, /huddle-watch in another session asks «Take over?» first; the automatic «always» start never takes over.

Effort and capacity

Each Issue says how big it is: 1 small, 2 medium, 3 large (2 when it says nothing). /huddle-issue suggests the effort from the Issue's own files, tests and migrations, and warns when an Issue is too big and should be split into parts.

Each Player has a capacity of 5 points by default, set by the Coach in huddle.json. With /huddle-play alone, the Player's session works on as many assigned Issues as fit at once, each in a subagent with a clean context, and starts the next one when room frees. Work in review uses no room, and two Issues that share a file never run at once. A Player can only lower their capacity, on their machine, with huddle capacity; huddle next shows what starts and what waits.

The Coach's watch does the same with the reviews: it reviews several pull requests at once within review_capacity points, and still merges them one at a time, checking each one again against the updated base first.

Staging

A project can test changes on a staging branch before they reach the default branch: set staging_branch in huddle.json (setup asks for it). Issue branches then start from staging and their pull requests target it. The Coach closes each Issue with huddle land once it is merged there, marks it tested with huddle tested after trying it in staging, and runs /huddle-release, which opens and merges the pull request from staging into the default branch only when every Issue in it was tested. Without a staging branch nothing changes.

«Only you» steps

The Coach's own session does every step it can: merging an approved pull request, tagging a release, running the smoke test on the sandboxes. It hands a step to a person only when it needs something the session cannot have:

  • a second person's account;
  • a payment;
  • a secret, such as creating or pasting a token;
  • a phone or another device;
  • a legal or business decision;
  • a paid action the person must approve;
  • a permission that was denied.

What such a step looks like

It is numbered, with one action per step and exactly where to click. Whatever is typed or pasted sits in a copy block. Each step ends with «You should see:» and «If you see something else:», and every technical word is explained once.
