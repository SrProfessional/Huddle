How a team works with Claude Code

Each person works with Claude Code on their own computer. Tasks arrive as Issues on GitHub or GitLab, ready to start, and Huddle keeps their status up to date by itself. This guide explains the cycle, the roles, the rules and how to start on your first day.

Our job is no longer typing code. It is making good decisions. The AI writes, tests and asks; the person decides.

The cycle

From an idea to merged code, step by step

  1. AI Manager

    Plans and splits the work

    The AI Manager defines what gets built, writes the spec and splits it into tasks that do not step on each other: each one touches different files. When one task needs another first, it says so under «Depends on».

  2. AI Manager

    Creates the Issue with its prompt ready

    With /huddle-issue, each task becomes an Issue from the template: the exact prompt to paste into Claude Code, the files that may and may not be touched, and the tests that must pass. Huddle assigns it to the person with the fewest open Issues.

  3. Developer

    Starts it with one command

    /huddle-play N checks that every dependency is merged, creates the branch in a folder of its own, marks the Issue in progress and runs its prompt. There is no need to explain the project: CLAUDE.md already gives the session the context. Run the same /huddle-play N again once the AI Manager has answered a review or a decision: the session sees the Issue is already started and continues it.

  4. Developer · this is where the value is

    Answers the AI's questions and decides

    The session asks what the Issue does not settle: what to do in an unusual case, what text the user sees, what to prioritize. Each answer is a decision, and the quality of the result depends on it. If the work cannot go on without the AI Manager, the session asks a «❓ Decision for the AI Manager» on the Issue and stops.

  5. Claude Code

    Writes the test, the code and opens the PR

    First the failing test, then the code that makes it pass. It opens a pull request (a merge request on GitLab) with the tests it ran and their real results, and closes with a message that starts with «✅ Issue #N finished». Then it keeps waiting for the review in the background.

  6. The platform

    Automatic tests and labels

    The project's CI runs its tests. Huddle's labels job moves each Issue through ready, assigned, in progress, in review and blocked, from its «Depends on» and its PR. Nobody moves those labels by hand.

  7. AI Manager

    Reviews: asks for changes or merges

    With /huddle-review, the AI Manager either comments a request with a «Prompt for Claude Code» block, which the waiting session takes by itself (marking it 👀), or approves and merges. A merged PR closes the Issue and unblocks the ones that depend on it. Anything that touches production or secrets is done only by the AI Manager. To have its session check by itself what waits, the AI Manager runs /huddle-watch (see «For the AI Manager»).

Roles

Who does what

AI Manager (a single person)

A person, not the AI: leads the work with the help of their own Claude Code session. Their login is ai_manager in huddle.json.

  • Decides what gets built and in what order.
  • Writes the specs and the Issues with their prompt.
  • Answers every «❓ Decision for the AI Manager».
  • Reviews and merges PRs. The only one who merges into the default branch.
  • The only one who touches production, settings and secrets.
  • Adds and removes people from the team.

Developer

Listed under assignees in huddle.json.

  • Takes an assigned Issue and works on its own branch.
  • Answers the session's questions with judgment.
  • Reviews what the AI did before the PR is opened.
  • If something does not fit the Issue, asks the AI Manager instead of improvising.
  • Never merges, never touches production.
The Issue

What each task brings

The Issue template makes every task arrive complete, so anyone's session starts the same way, no matter who takes it.

Goal
What we want to achieve and why, in a few lines.
Depends on
The Issues that must be merged first, one per line, or «None». Huddle keeps the Issue blocked until they are.
Branch
The name of the branch, created from an up-to-date default branch.
Prompt for Claude Code
The text the session runs, with the steps, the tests and how to open the PR.
Allowed files
The only things the session may touch. Anything else: ask first.
Contract or spec
The document that rules over the code.
Tests that must pass
What must pass before the PR, reported with real counts.
Labels

Where each Issue stands, at a glance

Huddle's labels job updates these on every change (on GitLab, by a schedule every 10 minutes). Filter the Issue list by a label to see, for example, everything waiting for review.

ready
Its dependencies are merged and nobody has it yet.
assigned
Someone has it but has not started.
in progress
Its session started it, or took a request from the AI Manager.
in review
Its PR is open and waiting for the AI Manager.
blocked
It waits for an Issue under «Depends on» to be merged. Closing that Issue by hand does not count.
needs decision
The session asked the AI Manager a question and stopped.
changes requested from AI Manager
A review request is waiting for the session to take it.

The stop labels. needs decision and changes requested from AI Manager mean the work waits for someone else, so they stand alone: in progress and in review are taken off while one of them is on, and come back by themselves once the request is taken or the question is answered. Nobody removes them by hand.

Progress

How far each area has come

Each area of the project (for example «Content», «Social networks», «Ads») is a milestone, and each Issue belongs to one. The AI Manager writes in each milestone's description how many Issues are still missing, on a line Huddle remaining: N. Huddle then shows, per area and in total, the merged Issues over all the work the area will need:

  • in a pinned «Huddle progress» Issue that the labels job keeps up to date;
  • with huddle progress (ask Claude Code «run huddle progress»);
  • in one line when a session opens, for example Content 76% · Social networks 55% · Ads 0% · Total 58%.

Issues closed by hand or «not planned» do not count, and Issues with no milestone stay out of the percentage.

Not sure which areas to use? The AI Manager runs /huddle-areas. Claude reads the README, the specs and the Issues, proposes the areas with the reason for each (as many as the project needs), puts the Issues that have no area in one, and suggests how many Issues are still missing in each. It explains first and changes nothing until the AI Manager says yes. It can be run again later to check that the areas are up to date.

Why

Why working this way is better

Before

  • Most of the time went into writing code by hand.
  • Each person explained the project in their own way.
  • Tasks collided in the same files.
  • Mistakes showed up late, in review or in production.

Now

  • The person's time goes into deciding and reviewing.
  • Every session reads the same context and the same rules.
  • Each task has its own files: two people do not collide.
  • Tests and review catch mistakes before merging.

The decision is the work

The AI is fast at writing and testing, but it does not know the business, the users or the priorities. When it asks, the person brings what the AI does not know. A good answer saves hours; a rushed answer is paid for later.

A ready prompt removes variation

If each person writes their own request, each session understands something different. With the prompt written by the AI Manager, they all start with the same goal, the same limits and the same tests.

Clear limits, fewer collisions

Allowed and forbidden files let several people move forward at once without stepping on each other, and tell the AI where not to go.

Production in a single pair of hands

Nobody on the team needs keys or access to production. A mistake in one session cannot touch what customers use.

A frequent question

Why doesn't a developer open 10 sessions to take 10 Issues at once?

It sounds faster, but in practice a developer with many open sessions gets less done and decides worse.

The computer becomes the bottleneck

Each session runs tests and builds. With many at once, the machine slows down and they all move more slowly than a few would.

Attention does not multiply

Each session asks questions. With ten open, the questions pile up, you lose the thread and start answering fast just to get through. That is when the decision stops being good, and the decision is exactly what the person brings.

Every session has to be reviewed

Ten half-reviewed PRs are worth less than two done well, and they fill up the AI Manager's review queue.

Our recommendation: one or two active sessions per person. Huddle assigns at most a few open Issues per person for the same reason. More speed comes from adding developers, not from adding windows.

Rules

What is not negotiable

  • Never push to the default branch. One task is one Issue, one branch and one PR. Only the AI Manager merges.
  • Only the allowed files. If another one is needed, ask first.
  • Test first. Write the failing test, then the code. The PR says which tests were run and with what result.
  • No production and no secrets. If a permission or a key is missing, stop and tell. Do not look for another way.
  • Nothing is dropped silently. Everything the Issue asks for ends up done, or listed under «What was NOT done» with the reason.
  • Close the task clearly. Every session ends with «✅ Issue #N finished» or «⛔ Issue #N stopped», the PR link, the test counts and your next step. If you do not see that message, the session is not over.
  • Chat in your language; the repository is in English. Commits, PRs, Issues, code comments and new documents are in English.
For the AI Manager

Setting up, adding people, watching and updating

  1. Put Huddle in the repository

    On a branch, run /huddle-setup. It asks the platform, the project, the AI Manager and the team, then writes huddle.json, the Issue and PR templates, the labels job, the Huddle block of CLAUDE.md and .claude/settings.json. Merge it with a PR, then ask Claude Code «run huddle doctor». If its login line says «gh is not installed or not on the PATH» (or glab), the tool is missing from that terminal: it gives the install command, and on Windows you open a new terminal afterwards. «Is not logged in» is a different message, with gh auth login or glab auth login as the fix.

    On GitLab two more things, only by you: a project access token with the api scope stored as the masked and protected CI variable HUDDLE_TOKEN, and a pipeline schedule */10 * * * * on the default branch. Never paste the token in a chat or a file.

  2. Add someone to the team

    Invite them to the repository (GitHub: Settings, Collaborators; GitLab: Manage, Members, role Developer). Then run /huddle-team: it checks that the login can be assigned, adds it to assignees in huddle.json through a PR, and gives you the message to send them with the install steps. huddle team lists the team and shows who cannot be assigned yet. Once that PR is merged, Huddle assigns them ready Issues.

  3. Let the session review by itself

    Run /huddle-watch (also /huddle-watch status and /huddle-watch off). Every few minutes the AI Manager's session checks what waits and reviews it. Turning it on is the order to merge what it approves; decisions and bug triage stay with the person. huddle queue lists what waits (ask Claude Code «run huddle queue»). The watch lives only in that session: closing Claude Code ends it.

  4. Update a project to a new release

    Install and update are per project, so do this in each project where Huddle is used. In a terminal, from the project's folder, run claude plugin marketplace update huddle and then claude plugin update huddle@huddle --scope project, and open a new session. Then, on a branch, run /huddle-update: it refreshes the templates and the CLAUDE.md block and asks only the questions a new release added. A project can be on an older version than another; claude plugin list shows each one. In the VS Code extension, which has no claude command in a terminal, type /plugins and use the same dialog to install (Install for this project) or update it.

    A newer release is announced in the chat by /huddle-play and /huddle-update, at most once a day. huddle notice says the same on demand.
